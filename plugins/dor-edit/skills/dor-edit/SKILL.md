# עורך רוח — /dor-edit

עריכה עיתונאית מלאה של טיוטה, מקצה לקצה, בסגנון העריכה של דור. **התוצר המרכזי: מסמך Google Docs שבו כל העריכות הן הצעות (suggestions) אמיתיות של Docs** — accept/reject מובנה של גוגל, כירורגי פר-שינוי, **מיוחסות לדור אישית ובלי שום תגית** — כך שאפשר לשלוח אותו ישירות לכתב/ת. הפירוט במסלולי המסירה למטה.

מסלולי מסירה (מעודכן 19.07.2026):
- **ברירת המחדל — מסלול א: `writeControl.writeMode: SUGGEST` ב-Docs API.** בונים `edits.json` ומריצים `upload_to_gdocs.py --suggest`: כל שינוי נכתב כהצעת Docs אמיתית בקריאת API אחת, בלי דפדפן — החלפה = הצעת-מחיקה של הישן + הצעת-הוספה של החדש; תוספת = הצעת-הוספה; הערות דרך Drive API. **הצעות נקיות, מיוחסות אישית לחשבון המאמת, בלי תגית `suggestIdImport`.** אומת מקצה לקצה 19.07.2026 (`suggest.*` נקי; בתצוגת PREVIEW_WITHOUT_SUGGESTIONS המקור נשמר → אין דריסה). דורש שהטוקן יהיה מהפרויקט `dor-gmail-mcp-30778` (`719854974771`) שאושר ל-Google Workspace Developer Preview Program (17.07.2026) — הסקריפט כבר משתמש בטוקני gmail-multi מהפרויקט הזה. **אימות חובה מובנה:** `suggest_edits` קורא חזרה עם `SUGGESTIONS_INLINE` ומחזיר `clean`/`overwrote` — אם `overwrote:true` (0 הצעות עם עריכות פעילות) SUGGEST נבלע לדריסה, **עצור והתריע**, אל תמשור.
- **אופציה משנית — מסלול ב: הצעות דרך docx-import (עם תגית).** בונים docx עם track changes בשם "דור זומר" (דרך hamakom-edit-core), מעלים וממירים ל-Google Doc → הצעות נייטיביות אמיתיות, אבל עם תגית `suggestIdImport` בלתי-עקיפה (בלי ייחוס אישי ברמת המשתמש). היה ברירת המחדל עד 18.07; היום פולבק בלבד — אם מסלול א נכשל או SUGGEST מפסיק לעבוד. אומת 17.07.2026.
- **אופציה שלישית — visual-diff (`--propose`).** צובע כל שינוי (הוספה ירוק+קו-תחתון, מחיקה אדום+קו-חוצה, **הישן נשאר, לא נמחק**), בלי תגית אבל **לא הצעות אמיתיות** — טקסט צבוע בלבד, בלי אווטאר. הכרעה גורפת דרך `--resolve accept|reject`. סרגל האישור (`dor-edit-sidebar.gs`) לא-אמין (`getEditsList` נתקע) — לכירורגי עדיף מסלול א.
- **פולבק/דפדפן — Compare Documents בדפדפן.** הצעות אמיתיות מיוחסות לדור, אבל דורש כרום ו"שורף טוקנים". רלוונטי רק אם ה-API כולו לא זמין. הרצף המלא בסוף שלב 6.
- **נפסל — יישום עריכות אחת-אחת בדפדפן במצב Suggesting.** נוסה בריצה הראשונה (03.07.2026): 30+ דקות לכתבה, שביר, ודור אמר "יכולתי לערוך לבד". **אל תחזור לזה.**

### 6. מסירה — הצעות אמיתיות דרך SUGGEST (מסלול א, ברירת המחדל; נקבעה 19.07.2026)

**העיקרון:** בונים `edits.json` ומריצים `upload_to_gdocs.py --suggest` על מסמך המסירה. כל שינוי נכתב כ**הצעת Docs אמיתית** בקריאת API אחת, בלי דפדפן — accept/reject מובנה של גוגל, כירורגי פר-שינוי, **מיוחס לחשבון המאמת (דור) ובלי שום תגית**. אומת מקצה לקצה 19.07.2026: מזהי `suggest.*` נקיים (`tagged: 0`), ובתצוגת `PREVIEW_WITHOUT_SUGGESTIONS` המקור נשמר — כלומר אין דריסה, חוק הברזל נשמר. עובד כי הטוקן מהפרויקט `dor-gmail-mcp-30778` (`719854974771`) אושר ל-Developer Preview (17.07.2026), והסקריפט כבר משתמש בטוקני gmail-multi מהפרויקט הזה.

**מבנה `edits.json`** (רשימת אובייקטים; שדות בכינויים גמישים — `originalText`/`find`/`anchor`, `newText`/`text`):
- החלפה: `{"type": "replacement", "originalText": "<טקסט קיים ייחודי>", "newText": "<החלופה>"}` — אפשר `"occurrence": N` אם המחרוזת חוזרת.
- הוספה: `{"type": "insertion", "anchor": "<טקסט קיים לעיגון>", "newText": "<מה שמוסיפים>"}` — נכתב **אחרי** העוגן, בלי לגעת בו. בלי `anchor` — נכתב בראש המסמך.
- מחיקה בלבד: `replacement` עם `"newText": ""`.
- הערה: `{"type": "comment", "anchor": "<טקסט קיים>", "comment": "<ההערה>"}` — נוספת כהערת Docs דרך Drive API. אם נכשלה — מדולגת ומתועדת ב-`comments_skipped`, ואז מעבירים אותה לדוח העורך.

**הרצף (מסלול א):**
1. הפק את `edits.json` מהחלטות שלב 4. שמור גם `edited.txt` (הטקסט המלא אחרי כל העריכות) כתיעוד.
2. בנה גרסה **נקייה** (בלי track changes — ההצעות נכתבות בשלב הבא), העלה כ-Google Doc — **זה מסמך המסירה עצמו**:
```bash
DE=$(ls -d ~/.claude/plugins/cache/hamakom-plugins/dor-edit/*/skills/dor-edit 2>/dev/null | sort -V | tail -1); DE=${DE:-~/.claude/skills/dor-edit}
python3 "$DE/scripts/build_docx.py" draft.txt delivery.docx        # המקור — כדי שעוגני edits.json יימצאו
python3 "$DE/scripts/upload_to_gdocs.py" delivery.docx --name "<כותרת> — עריכת דור"
```
   הכלל: המחרוזות ב-`edits.json` (`anchor`/`originalText`) חייבות להופיע בטקסט של המסמך שמעלים — לכן מעלים את **המקור** (`draft.txt`), וההצעות מסמנות את הדיף מולו.
3. החל את ההצעות על מסמך המסירה:
```bash
python3 "$DE/scripts/upload_to_gdocs.py" --suggest edits.json --doc <doc_id>
```
   הפלט (JSON) מדווח `applied`, `suggestions` (`insertions`/`deletions`/`tagged`), `comments_added`, ו-`skipped` (עוגנים שלא נמצאו — תקן מהטקסט החי והרץ שוב). **בדיקת אימות חובה:** ודא `"clean": true` ו-`"overwrote": false`. אם `overwrote:true` (0 הצעות עם עריכות פעילות) — SUGGEST נבלע לדריסה, **עצור מיד, אל תמשיך**, והתריע לדור (סימן שהאישור/הטוקן נשבר); הפעל פולבק מסלול ב.
4. **הכרעת דור — פר-שינוי מובנה של גוגל.** דור מקבל/דוחה כל הצעה בנפרד ישירות ב-Docs (accept/reject אמיתי, אמין). אין צורך בסרגל או ב-`--resolve` — זה היתרון המרכזי על visual-diff.

**סבב המשך על מסמך שדור כבר סקר:** לפני `--suggest` נוסף — קרא את המצב הנוכחי (`documents.get`): דור מקבל/דוחה בין סבבים והטקסט החי השתנה. מחרוזות ה-`anchor`/`originalText` חייבות להילקח מהטקסט **הנוכחי**. הצעות חדשות לא נוגעות בהצעות פתוחות; מה שלא נמצא מדווח ב-`skipped` בלי לפגוע בקיים.

---

**פולבק — מסלול ב: הצעות דרך docx-import (עם תגית).** רק אם מסלול א נכשל (`overwrote:true`, או SUGGEST הפסיק לעבוד). בונים docx עם track changes בשם "דור זומר" דרך hamakom-edit-core (שלב 4), מעלים וממירים — ההמרה מייצרת הצעות נייטיביות אמיתיות, **אבל עם תגית `suggestIdImport` בלתי-עקיפה** (בלי ייחוס אישי ברמת המשתמש; אומת 17.07.2026 שהעלאה מהטוקן של דור אינה מסירה אותה):
```bash
DE=$(ls -d ~/.claude/plugins/cache/hamakom-plugins/dor-edit/*/skills/dor-edit 2>/dev/null | sort -V | tail -1); DE=${DE:-~/.claude/skills/dor-edit}
EC=$(ls -d ~/.claude/plugins/cache/hamakom-plugins/*/skills/hamakom-edit-core 2>/dev/null | sort -V | tail -1); EC=${EC:-~/.claude/skills/hamakom-edit-core}
python3 "$EC/scripts/office/pack.py" <workdir> edited-tracked.docx
python3 "$DE/scripts/upload_to_gdocs.py" edited-tracked.docx --name "<כותרת> — עריכת דור"
```
אמת ב-`documents.get` `suggestedInsertionIds`/`suggestedDeletionIds` לפני שממשיכים.

**פולבק — visual-diff (`--propose` + `--resolve`; בלי תגית אבל טקסט צבוע, לא הצעה אמיתית).** צובע כל שינוי (הוספה ירוק+קו-תחתון, מחיקה אדום+קו-חוצה, **הישן נשאר, לא נמחק**). הכרעה **גורפת בלבד** דרך `--resolve` (הסרגל `dor-edit-sidebar.gs` לא-אמין — `getEditsList` נתקע):
```bash
python3 "$DE/scripts/upload_to_gdocs.py" --propose edits.json --doc <doc_id>
python3 "$DE/scripts/upload_to_gdocs.py" --resolve accept --doc <doc_id>   # מוחק את הישן-האדום, משאיר את החדש
python3 "$DE/scripts/upload_to_gdocs.py" --resolve reject --doc <doc_id>   # מוחק את החדש-הירוק, מחזיר את הישן
```

**פולבק אחרון — Compare Documents בדפדפן (הצעות אמיתיות מיוחסות; שורף טוקנים).** רק אם ה-API כולו לא זמין. בנה גרסה ערוכה זמנית, ואז בכרום (mcp__claude-in-chrome): פתח את מסמך **המקור**, Tools, Compare documents, בחר את הזמני, Attribute differences to: דור זומר, Compare. **כללי דפדפן:** בלי קיצורי Cmd (תפריטים בלבד); ודא בצילום מסך שהדיאלוג פתוח לפני הקלדה; בלי cmd+a (triple_click בלבד). מחק את הזמני בסוף (drive_trash).

### 8. דוח עורך — לשונית **בתוך** המסמך (חובה; לא מסמך נפרד)

דרישת דור (17.07.2026): **הדוח לא נמסר בנפרד — הוא נכנס כלשונית בשם "דוח עורך" בתוך אותו Google Doc.** הגוף הראשי נשאר בלשונית הראשית.

כתוב `report.txt` **במארקדאון מלא** ואז, על מסמך המסירה:
```bash
DE=$(ls -d ~/.claude/plugins/cache/hamakom-plugins/dor-edit/*/skills/dor-edit 2>/dev/null | sort -V | tail -1); DE=${DE:-~/.claude/skills/dor-edit}
python3 "$DE/scripts/upload_to_gdocs.py" --report-tab report.txt --doc <doc_id>
```
הסקריפט יוצר את הלשונית (`addDocumentTab`) ו**מרנדר את המארקדאון לאלמנטים אמיתיים של Docs** (מאז 19.07.2026). Google Docs אינו מרנדר מארקדאון — לפני התיקון הדוח נשפך כטקסט גולמי (צינורות במקום טבלה, כוכביות, `---` מיותם, URL חשוף), ודור פסל אותו כ"בלתי קריא". מה שנתמך עכשיו:

| כתוב ב-report.txt | מתקבל במסמך |
|---|---|
| `\| א \| ב \|` + `\|---\|---\|` | **טבלת Docs אמיתית**, שורת כותרת מודגשת |
| `[טקסט](url)` | **קישור חי על הטקסט** (לא URL חשוף) |
| `**מודגש**` | הדגשה אמיתית |
| `#` / `##` / `###` | HEADING_1/2/3 בגדלים 20/17/15 |
| `- פריט` / `1. פריט` | בולטים/מספור אמיתיים |
| `---` | מושמט (לא מקפים במסמך) |

**חובה: אימות עובדות וחומרים להרחבה נכתבים כטבלה ומקורות כקישורים** — זה מה שהופך את הדוח לקריא. הפונט נאכף ברמת ה-run ולכן הדגשה שורדת (weight 700), והכותרות מקבלות את גדלי ההיררכיה.

**סימון כותרות הכתבה עצמה (בלשונית הראשית):** כדי שהכתבה תגיע לכתב/ת עם מבנה אמיתי ולא טקסט שטוח —
```bash
python3 "$DE/scripts/upload_to_gdocs.py" --mark-headings headings.txt --doc <doc_id>
```
`headings.txt` = שורה לכותרת, עם `#` לראשית ו-`##` לכל כותרת ביניים (ברירת מחדל בלי קידומת: H2). הסקריפט מתאים לפסקה הקיימת ומחיל עליה `HEADING_1/2` + RTL + הגודל הנכון. **זו פעולת עיצוב ולא תוכן** — לא נמחקת אף מילה — ולכן מותרת תחת חוק הברזל. הפלט מדווח `marked` ו-`not_found` (כותרת שלא נמצאה מילה-במילה — תקן מהטקסט החי).

**אכיפת פונט על מסמך שלא נבנה מ-build_docx.py** (למשל תוצר Compare, שיורש את הסגנונות של מסמך הכתב/ת):
```bash
python3 "$DE/scripts/upload_to_gdocs.py" --enforce-font --doc <doc_id> [--only-tab <tab_id>]
```
עיצוב אינו דריסת תוכן, ולכן מותר בלי עצירה. הפקודה נוגעת רק בפונט ובגודל-גוף — הדגשה, נטוי, צבע וקישורים של דור שורדים. הרץ אותה על **מסמך מסירה טרי**; אם דור כבר עיצב את הלשונית הראשית, הגבל ללשונית הדוח עם `--only-tab`.

**חוק הברזל חל כאן — ומשמעותו לְהוסיף, לא לעצור:** אם הלשונית "דוח עורך" כבר קיימת, הסקריפט **מוסיף בסופה** עם מפריד מתוארך, ולא בונה אותה מחדש ולא דורס. הוספה בסוף לא מוחקת דבר. אין לעצור בגלל שהמסמך השתנה — קרא את מצבו העדכני והמשך.

מבנה הדוח (הלשונית חיה בתוך הכתבה; **הלשונית הראשית נשארת נקייה ושליחה לכתב/ת**):
1. **אימות עובדות** — **טבלת מארקדאון** בת 4 עמודות: סטטוס (מאומת / לא נמצא אישוש / סותר / מיוחס-לדובר) | הטענה | המקור שנמצא | הערה לכתב/ת. המקור תמיד כקישור `[שם המקור](url)`, לא URL חשוף.
2. **חומרים להרחבה** — מקורות ראשוניים (דוחות, פרוטוקולים, פסיקות), מומחים/גורמים שלא צוטטו, כתבות קשורות שלנו ושל אחרים — כרשימת בולטים, כל מקור כקישור על שמו.
3. **כותרות** — הכותרת שנבחרה, 2–3 חלופות, כותרת SEO, תיאור מטא, מילות מפתח.
4. **תמונות פלאש 90** — קישור חיפוש לכל שאילתה + מזהי תמונות מועמדות.
5. **החלטות דור** — 3–7 נקודות שרק הוא מכריע, ממוינות לפי חשיבות (תגובות חסרות, סוגיות אתיות, בחירות מסגור).

## חוקים קשיחים

- שום עובדה חדשה בגוף בלי מקור בהערה צמודה. ספק = הערה, לא תיקון. עובדה שגויה שאין לה תיקון ודאי — נמחקת.
- עדויות לא מקוצצות. ציטוטי מחץ מקודמים בלי לשנות מילה.
- בטור דעה: אין שינויי מבנה, אין ריכוך רטוריקה — שגיאות בלבד.
- SSL בסקריפטים: certifi כבר מטופל. אם python נכשל על מודול — `pip3 install <מודול> --break-system-packages`.
